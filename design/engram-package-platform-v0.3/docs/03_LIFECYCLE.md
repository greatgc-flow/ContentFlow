# Lifecycle transactions, recovery and state integrity

## 1. Single coordinator and commit boundary

Existing Engram env_lock/env_ops are the first choice. #145 registry publication is standalone and calls env_ops; a nested `publish()` under manager lock would contend or replace an active journal. In WP3 establish one shared transaction context with fixed trusted step factories. Extract pure registry prepare/validation and safe journaled step only when needed; preserve standalone caller behavior with regression. Do not call vendor code to generate executable steps. Journal and registry snapshots have bounded size, redacted metadata and hashes, never raw auth. Existing CRC is torn-write evidence, not malicious-user authentication.

A lifecycle mutation has one parent op (installation identity, operation id, expected revisions, intent/plan digest, expiry and prior service state); child effects have deterministic ids derived from parent/package/step and request digest. Acquire the existing exclusive lifecycle gate first; revalidate plan digest, approval, trust freshness, current registry revision, root identity, ownership, disk, provider facts before any effect. Non-mutating metadata read can happen without write lock; apply must revalidate. No nested `env_ops.execute`, second registry writer or package-owned host-install process. Package domain transactions use their own DB locks only inside a bounded adapter step. No network while DB transaction held. Runtime groups and pack locks ordered by canonical ids; never reenter coordinator from adapter. Do not hold GPU lease while waiting for lifecycle dependency. Never wait indefinitely for an app.

Two registry files (Python and pack) are not physically one atomic write: journal exact old/new images and commit intent, gate all managed launches and mutations while nonterminal journal exists, publish with checked revision and crash seam after each pointer, revalidate coherence, final commit only after group pointer+health conditions. Pure status may read incomplete state, must report IN_PROGRESS/RECOVERY_REQUIRED, not installed healthy. Writer/gate also coordinates application launch admission: short lock verifies generation/revisions then registers owned launch intent/lease before process start; final check under same gate binds process identity or quarantines uncertain launch. Do not hold lifecycle lock for entire normal app session. During update block new launches, quiesce registered old processes, verify exact owned handles. If cannot establish ownership or drain -> refuse/blocked. Direct execution of obsolete raw binary outside managed launcher is unsupported and cannot be promised fenced.

## 2. Lifecycle phases and authoritative state

| Phase | Entry/exit requirement | Crash/exception action |
|---|---|---|
| PLAN | immutable plan from trusted metadata, scope, current revisions, explicit preconditions; no state mutation | discard; no successful effect |
| APPROVED | exact plan digest, installation/root, trust/policy version, expiry, risk category and actor verified; normal yes != data deletion/paid/publish | expired or changed -> replan |
| INTENT_RECORDED | gate acquired, same facts, journal created and effect IDs recorded, launch fence active | no recorded effect -> explicit abort/recovery |
| STAGED | archive admitted, verified exact members, staged immutable app/runtime/env at final unique unpublished path, no active pointer change | reconcile staged bytes by receipt; clean only owned disposable stage |
| VERIFIED | native canary, manifest/probe/rights/disk, no irreversible business effect | reject candidate; old generation untouched |
| DRAINED | new admission closed, prior service state recorded; owned processes drained, consistent data checkpoint if necessary | if partial, inspect and safely restore only prior service state; unknown -> block |
| APPLYING | record pre-effect receipt; runtime and app pointers/coherent domain migration in prescribed order; fence all managed readers/launchers | compare actual state to old/new images; known old -> retry idempotent, known new -> acknowledge, divergent -> RECOVERY_REQUIRED |
| COMMITTED | all group authoritative pointer images and compatible schema/data published, verified; record exact group result | not pre-commit rollback; post-failure separate |
| HEALTHY | required bounded local health/fixture validated; restart only previously running services allowed by policy | if reversible, journal compensating pointer+data restore; otherwise recovery-required; do not lie about rollback |
| COMPLETE | final durable receipt, re-open gate for safe group, retain rollback assets | replay op returns receipt, no effect |

If an adapter health can be proved before commit, prefer candidate isolated canary and verify old/new schema pair before public activation. Postcommit failure must not be reported success. Rollback after a destructive schema migration requires matching verified snapshot and explicit acknowledgement of losing post-snapshot writes. P0 prohibit irreversible migration unless reviewed one-way gate and recovery plan; P0 fixtures use reversible schema only. Never imply a domain publication/paid remote effect can be undone by package rollback.

Outcomes: SUCCESS, NOOP, BLOCKED (precondition), CANCELLED (no mutation or clean abort), FAILED_ROLLED_BACK (verified prior state), PARTIAL (independent groups committed plus failed/blocked group, list exactly), RECOVERY_REQUIRED (unknown/divergence/failed compensation). No `PARTIAL` within an inseparable runtime/app/DB dependency group. No success if any requested group unresolved. Keep exit 0 only successful/no-op/preview; use existing Engram exit mapping in global calls, see CLI document. `--resume` matches op and trusted step identity, no fresh authorization or new unapproved effect; stale approval may permit only protective cleanup/rollback under journal scope, any new effect needs new plan. User-data purge cannot resume without exact verified intent and scope.

## 3. Install and update flow

Install: catalog id -> select profile/dependencies -> evaluate exact artifact compatibility, byte/expanded/scratch/rollback space + configured workspace reserve -> plan and explicit authorization -> download only approved artifacts into private cache (offline requires preexisting trusted pack), validate manifest signature/expected publisher+digest and members -> safe extract to isolated stage -> construct env at final unique immutable path -> verify candidate executable and lock -> acquire/record appropriate app state under parent operation -> stage domain layout without importing user sources -> publish binding -> bounded health -> receipt. On repeated install same profile+generation returns NOOP, no duplicated account/auth, services not auto-started. If slot foreign/retained, require explicit restore/reinstall plan and ownership; do not overwrite data. Direct `contentflow` or `ai` absent returns help/NOT_INSTALLED; not setup.

Update: check metadata only for installed packs with authorized network; separate `source latest`, `available artifact`, `compatible candidate`, `installed`. Unknown/stale is not current. `--offline` uses verified local metadata, explicit freshness/unknown. No cloud API calls. Policy permits compatible reviewed patches only; major, new license, profile/permission change, native provider/ABI change, one-way migration require separate explicit approval. Stage both versions; if app DB needs migrate, pre-check reversible adapter + checkpoint and candidate clone validation; no opening newer schema with old app. Retain prior generation and exact lock/binary refs until explicit GC criteria. Install missing optional feature requires explicit plan, never broad update. Default existing `engram update` plans existing scope first; once integration is qualified, installed pack safe updates join parent operation (global existing behavior preserved when absent). `engram pack update ID` scopes to that pack and required safety checks, not unrelated AI. Any missing shared runtime requiring mutation must be part of approved plan. No hidden upgrade of all consumers. Incompatible consumer stays pinned; release/GC protects all refs.

## 4. Detached core self-update and old executable

Current helper overlays staged files. Core artifact MUST exclude every package slot, all managed mutable generation/env/cache/state, not merely `*.log`/`data` names. Only reviewed static descriptor/wrapper and unchanged allowlisted Core assets. Parent journal written durable before helper; helper input contains immutable exact target list, old/new core hashes, install/root identity, parent PID+creation identity, protocol/generation, plan digest; helper validates path/ownership again. Stage and backup outside doomed target or protected location; wait for proven parent, bounded. Child helper effect receipt identifies actual changed core. After handoff new core reopens coordinator, verifies manifest/schema compatibility, parent receipt and exact plan, blocks launch until resolved; no arbitrary package adapter re-execution. If version/protocol or approval mismatch, finish core-only protective recovery; require fresh pack plan. Test old v3.11.13 updater reading candidate archive, new core with legacy no-pack roots, failed update, helper crash and downgrade. Older executable cannot enforce new pack guards; unsupported downgraded manager must never be advertised safe. No production enablement before integration gate. If impossible safely, keep explicit pack lifecycle and block risky global operation when installed rather than silent skip.

## 5. Backup, restore, relocation, clone and uninstall

A backup is not a file copy of an active store. Pack manager fences new launches/jobs, asks trusted adapter to drain and produce consistent checkpoint (SQLite online backup with app-wide artifact consistency or closed DB; PG supported native consistent backup), captures immutable objects/refs, domain schema and app/runtime lock, checks hashes and receipt, verifies restore in disposable target where feasible, stores external or preserved destination. Exclude secrets/token/session auth and external projects by default; data classification and manifest must state omissions, backup coverage and recovery needs. No global success if pack checkpoint fails. Read-only backup preview creates no directories. Legacy archive without pack section leaves pack untouched; unsupported schema or conflict refuses overwrite. Data-only restore on absent pack keeps it dormant, no installs or autorun. Restore to existing target staging and explicit replacement, never overwrite sole copy; restore prior image on failure. Restore may change trust lineage: all paid/publish/bot/job automatic authority disabled until reauthorized. Pending ambiguous remote action preserved and reconciled, never auto-replayed.

Move same installation only after managed source is quiesced; record move nonce, previous root fingerprint, inventory, verified checkpoint, source deactivation evidence or explicit operator attestation if disconnected. Never claim proof of source shutdown across hosts. At target re-evaluate physical system root and identity, reject reparse/sync/unsupported active DB filesystem, rebuild owned env/entrypoint at final target from offline cache; same-volume rename and cross-volume verified copy separate cases. No global rewrite historical evidence, DB content, workspace original paths or secrets. Cross-volume source preserved until target verification and explicit cleanup; clone gets fresh installation & workspace identity where domain requires, duplicate approvals/jobs disabled, no coactive remote effects. Moved data with no wheel/model -> capability blocked, not silently host fallback. Ordinary core relocate invokes applicable installed-pack checkpoint/relocation only after proof; absent no effect.

Pack remove: stop only proved owned processes; plan exact immutable program members, env/runtime refs, aliases, retained data. Remove binding and verified owned disposable assets, keep domain data, config, models, logs according policy and rollback/recovery metadata. Mark DATA_RETAINED; unknown files stay, missing path is not proof of deletion success for a live process. Never remove other pack or external workspace. Reinstall explicit chooses existing retained workspace or fresh; use schema compatibility guard. Reset legacy remains existing scope; separate `pack purge` only after backup verification, explicit typed scope+confirmation, no broad `--yes`, no external reference deletion. GC excludes active/previous/pinned/pending/snapshot/reference/unknown assets; if references cannot be proven refuse, never assume no reference from folder name.

Whole Engram uninstall: existing uninstaller preserves unknown top-level slots but removes `_sys/data`, `_sys/env`, static wrappers. Do not blanket-add `AI`/`ContentFlow`/`packages` to V326_SYS_PROGRAM_ENTRIES. Before helper/registry deletion, valid packs are drained, create self-contained recovery manifest/data checkpoint (including lock/artifact provenance; model assets either retained verified in place or exported) outside all deletion targets. If protected retained roots remain, output exact paths and restore/reinstall instructions; do not imply programs remain runnable. If whole root deletion intended, require verified external export or separate explicit purge consent. On unknown/corrupt pack state or checkpoint failure refuse destructive operation; owner may repair/export manually. Helper verifies original target list, identities and no reparse at effect, never recursively delete unowned trees; journal outside deletion targets. Legacy no-pack behavior exact. Old manager uninstall cannot be claimed to honor new protocol; supported upgrade/remove path documented.
