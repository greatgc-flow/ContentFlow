# Contract boundary (v1.0, proposed)

JSON Schema 2020-12 validates structural DTOs; schema IDs use `.invalid` intentionally and require no network. Each file embeds shared definitions for standalone validation. Before implementation extract common definitions or generate from typed models without changing semantics; verify no drift. All examples are synthetic and cannot be treated as real IDs, approvals, licenses, provider capabilities, media, financial evidence or remote receipts. No schema establishes an authority boundary by itself.

Normative domain checks in addition to schema: same workspace and valid referent/revision/hash; canonicalization per ADR A03; permission and data-class scope; nonnegative caps and reservations (ledger signed separately); currency scale per ISO/provider; freshness and time ordering; current revision/approval with exact intent digest and actor authorization; valid source page coverage and claim links; calculation formula allowlist (not arbitrary evaluation); source/asset retention; explicit disclosure/eligibility; DAG unique keys, acyclic graph, reachable input, optional dependency semantics and no remote effects in offline profile; job/step transition and lease fencing; resource/attempt caps; timeline scene/caption ordering and bounds, frame rounding; export relative path containment and actual artifact digest; external intent uniqueness, remote verification and unknown-charge reconciliation; metrics definition and period; ledger correction/settlement uniqueness. Test-only taint propagates and blocks public posting regardless of approval. Any cross-contract inconsistency fails release, not merely logs a warning.

Fixture hashes are deterministic placeholders; there are no actual media assets in this bundle. The real offline E2E fixture is created during TDD from owned/redistributable materials. Negative structural fixtures must be rejected; relational negative cases belong in planned domain tests. Future changes require schema migration and compatibility tests, not silent field renaming.

Portable extensions: `pack_manifest` and `move_manifest` define metadata only. Domain must verify detached signatures against a trusted key, sign/verify canonical manifest bytes (signature reference metadata included, signature bytes detached), validate each member's hash/size and path, dependency graph and platform, disk reserve, rights, no hidden credentials, exact activation state, current authority/reconciliation and deletion journal. A valid schema is never proof of trust or permission to install. Move snapshot authentication and archive integrity are required; local transfer may use owner-controlled trusted verification rather than a release-signing key. The synthetic examples reference no actual files or keys.
